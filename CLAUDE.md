## Working on the learning docs

The docs *are* the deliverable, so their form matters as much as their content.

- Written in **Vietnamese**, one file per step: `docs/learning/NN-<step>.md`, about one page, tables over prose.
- Standard sections: a `## Chốt` table (Việc / Chọn / Vì sao), an options table (Phương án / Ưu / Nhược / Quyết định), `## Không chọn` with a "Khi nào đổi" column, `## Rủi ro và kiểm chứng`, `## Bài học`, `## Tham khảo`.
- **Record the rejected options and why** — they carry as much of the learning as the chosen one, and each one names the condition that would reverse it.
- Brainstorm the step first: options, tradeoffs, a recommendation; the owner decides. Ask only what is genuinely their call. If they answer a question with a question, answer theirs first, then re-derive the recommendation.
- Verify library versions, licenses and behavior against PyPI or the source before recording them. Several decisions here turned on a license (jina → CC-BY-NC) or a token limit, and the docs log cases where a summarizing tool fabricated facts about the corpus.
- After each decision: write/update that step's doc **and** the progress table in `CAPABILITY-MAP.md`.

## Architecture

Six modules, built in dependency order — `ingest` → `index` → `retrieve` → `generate` → `ui`, with `eval` written early and re-run after each one. `CAPABILITY-MAP.md` is the authoritative version of this table.

Query path: dense ∥ BM25 → RRF → rerank → top-1 above threshold? if yes context reorder; if no PageIndex fallback → enough evidence? if no answer "không biết" → LLM → answer + citation → Streamlit with a trace panel.

### Locked-in stack

Core logic (RRF, fallback threshold, context reorder, prompt + citation assembly) is hand-written on purpose; libraries only for parsers, embedding, vector store and BM25. **No LangChain, no LlamaIndex.** Fetching is `httpx` reading `__NEXT_DATA__` JSON directly (DOM/`BeautifulSoup` scraping and Crawl4AI are fallbacks for the rare page without JSON, not the main path); conversion/OCR is Docling; embedding is bge-m3 via sentence-transformers (local, MPS); storage is LanceDB (cosine, flat scan, no ANN) plus bm25s; the LLM sits behind a thin adapter (Ollama `qwen2.5:3b` in dev — switched from `qwen3:4b` 2026-09-22 after live latency measurement, see "Generate gotchas" — Claude API when quality matters). Token counting at chunk time uses the real bge-m3 tokenizer (`transformers.AutoTokenizer`, tokenizer-only — no torch pulled in) rather than a word→token estimate, since `docs/learning/02-chunking.md` already flagged the old estimate as provisional.

### Ingest gotchas (found by running against live data, not guessed)

- **CMS rich-text fields mix in raw HTML.** Some `description`/answer strings contain `<strong>`, `<i>`, `<a href>` inline — inconsistently, not every document uses them for the same thing (e.g. `generalItems[0]`'s headings are bare `"1. TITLE"` lines, but `generalItems[2]`'s are `<strong>1. TITLE</strong>` — lose that and you silently lose that document's top-level headings). `heading.strip_inline_html()` runs before every heading match; call it (or `heading.classify_line`, which already calls it) rather than matching raw JSON strings.
- Line breaks inside these JSON strings are literal `\r\n`, not markdown blank lines — `heading.split_lines()` handles this.
- Don't assume a JSON field's shape from one example; `insuranceData.columns` looked like it should be a list of column defs and was actually a delimited string. Print/inspect the real fetched structure before writing a parser for a new page.
- **Bug thật 2026-09-23: "page no longer exists" can mean "wrong URL guess", not "page is gone".** The E-Green wallet terms page was marked unresolved because the original inventory's URL (`/e-green-wallet-payment-terms`) 404s — but every *other* policy page on this site lives at `/vn-vi/terms-policies/<slug>`, and nobody had tried that exact prefix for this page specifically. It resolved immediately once tried: `/vn-vi/terms-policies/e-green-wallet-payment-terms`, HTTP 200, real content (`rag_gsm/ingest/extractors/egreen.py`). Before declaring a page gone, try every URL *pattern* already confirmed to work for sibling pages, not just the one literal URL a stale doc recorded. Also: this page's `pageProps.serviceData` reuses the same top-level key as `service-agreement`'s `serviceData.serviceItems[]`, but here `serviceItems` is `null` and the real text is in a single `serviceExcerpt` string (same shape as one `generalItems[i]` entry) — same field name, different shape, another instance of the `insuranceData.columns` lesson above.

### Chunk gotchas (found by running against live data, not guessed)

- **`doi_tuong` boundaries only make sense at real khoản level.** Applying the label-boundary rule per *paragraph* to documents with no heading numbering at all (`phu-luc-01/13/15` — plain prose, e.g. a step-by-step user flow that naturally alternates "Người dùng làm X" / "Đối tác làm Y" mid-narrative) shredded a single coherent procedure into dozens of near-empty chunks. Fixed in `rules.py`: the label-boundary rule applies only when `node.children` came from real document numbering; headingless text is packed by size only, and `doi_tuong` is assigned *after* packing, for metadata/filtering, not as a hard boundary.
- The introductory phrasing `02-chunking.md` expected the `doi_tuong` regex to key off ("Đối với Đối Tác", "Nếu Bạn là Người dùng") doesn't match how the real clauses are written (`"4.1. Người dùng phải tuân thủ..."`, `"4.2. Đối tác phải tuân thủ..."`). `label_doi_tuong()` instead checks for the *presence* of "đối tác" vs "người dùng"/"khách hàng" in the clause's own text.
- **Bug thật 2026-09-23 (found via a corpus-wide chunk_id uniqueness check written while validating the OCR work, not by inspecting any one document): `chunk_id` was not actually guaranteed unique.** Two real cases, both now fixed in `rules.py`: (1) `phu-luc-14-tai-khoan-gia-dinh.md` has three independently-numbered `# 1.`/`# 2.`/... lists back to back (rules for "Chủ tài khoản", then "Thành viên", then "Đối tác Tài xế" — informal plain-text dividers, not real headings), so two completely different clauses both landed on `so_muc="1"` and thus the identical `chunk_id`; (2) a heading with no numeric prefix at all (first hit by the OCR'd `quy-che-hoat-dong.md`, e.g. "Quy trình đổi trả hàng và hoàn tiền") made `so_muc` `None`, and every such heading in one document collapsed onto the same bare `chunk_id = doc.doc_id` once its content needed splitting — `_breadcrumb` also printed a literal `"None-None"` in this case. **Why this matters more than a cosmetic id clash**: `chunk_lookup` everywhere in this codebase (`ui/app.py`, `generate/answer.py`) is built as `{c.chunk_id: c for c in chunks}` — a duplicate id means one of the two colliding chunks silently vanishes from lookup, so if it's ever retrieved and cited, the citation would resolve to the *other* chunk's text/heading_path instead, with no error. Fixed with two changes: `_make_chunk_from_leaves`/`_split_oversized_leaf` fall back to a slug of the heading's own title (new `_slugify()`) instead of a fixed `"1"`/`None` when `so_muc` is missing; and `chunk_document()` now runs every doc's output through `_dedupe_chunk_ids()`, which appends `-2`, `-3`, ... to any id that still repeats, as a defensive last resort that doesn't depend on knowing why a collision happened. `tests/test_chunk_rules.py` has a regression test for each case. This was a pre-existing bug in the already-shipped corpus (`phu-luc-14`), not something the OCR work introduced — it was just never checked for before.

### OCR gotchas (found by running against live data, not guessed)

- **OCR engine bake-off (2026-09-23), Docling with 3 candidate backends on 3 sample pages (1, 30, 56): `OcrMacOptions` (Apple Vision, built into macOS, no download) won clearly.** ~4-5s/page, near-perfect Vietnamese diacritics, correct reading order. `EasyOcrOptions` was both slow (44s/page) *and* scrambled the reading order on a two-column header (words dropped/reordered) despite decent diacritics. `RapidOcrOptions`' default model is Chinese-only and produced text with almost no Vietnamese diacritics at all (e.g. "CÔNG TY C PHÀN" instead of "CÔNG TY CỔ PHẦN") — not a config mistake, that model genuinely has no Vietnamese support. **Real quirk**: macOS Vision reports Vietnamese as the nonstandard BCP-47 tag `"vi-VT"`, not `"vi"` or `"vi-VN"` — `lang=["vi"]` raises `OcrLanguageNotSupportedError`; Docling's own source has a comment acknowledging this exact Vision bug. Use `OcrMacOptions(lang=["vi-VT"])`.
- **Running OCR on all 56 pages revealed this is not one uniform legal document.** Real structure: pages 1-2 (title + preamble), pages ~2-42 ("Quy trình dành cho Khách Hàng" then "...Tài Xế" — step-by-step app-usage tutorials as 2-column tables, screenshots on the right, driver-facing content mixed in and out of customer scope), pages 43-46 and 52-56 (real legal/procedural prose: refund process, dispute resolution, payment methods, platform/merchant obligations), pages 47-51 (another screenshot-table interlude, promotions feature). **On the 2-column screenshot-table pages, Docling's page-level OCR pipeline lost the actual text entirely on 17 of 56 pages (~30%)** — output was just the placeholder `<!-- image -->` — even though the instructional heading text ("Bước 2: Tạo tài khoản...") is clearly legible bold print in the source image. This is a layout-classification failure (the whole page got treated as one picture), not a language/diacritic problem, and it wasn't worth solving for content that mostly duplicates the FAQ anyway.
- **Scope decision (user's call, not assumed): OCR/index only the reliable, high-value prose pages (1-2, 43-46, 52-56 — 11 of 56) and skip the screenshot-table tutorial sections (customer and driver/merchant) entirely.** The step-by-step "how to book/create an account" content there is lower-value (already covered better by the clean-JSON FAQ) and unreliable to OCR at the page level; re-visit only if eval shows a real gap. See `rag_gsm/ingest/ocr_regulations.py` for the exact page list and full reasoning trail.
- The final `data/markdown/quy-che-hoat-dong.md` body (checked in as `rag_gsm/ingest/quy_che_hoat_dong_body.md`) is **hand-cleaned from real OCR output, not purely mechanical** — obvious OCR typos were fixed, and pages 53-55's numbering (`"1.1.1."` repeated verbatim for many unrelated bullets — a real OCR/source-list misread, confirmed against the source image) was deliberately dropped rather than encoded as fake `so_muc`, relying on the same size-based packing already used for `phu-luc-01/13/15`'s unnumbered prose. Re-OCRing (e.g. with a better engine later) means re-reading and re-cleaning by hand again, not regenerating automatically — `ocr_regulations.py`'s `ocr_page()` is for spot-checking against the source, not for overwriting the curated file.
- `trang_bat_dau`/`trang_ket_thuc` (page-number citation fields, `Chunk`/`Citation` in `schemas.py`) are **still always `None`, including for this OCR'd document** — threading real page numbers through `chunk/rules.py` (shared by every `dieu_khoan`/`chinh_sach` doc) was judged not worth the regression risk for an MVP pass; citation still works via source URL + heading path. Revisit if citing a specific OCR page number ever actually matters.
- **Real, unresolved data-quality finding, not something to silently pick one answer for**: this one document alone contains three different phone numbers for "liên hệ khiếu nại" — `1900 2097` / `19002097` (page 43/45, "Tổng đài hỗ trợ") and `1800 1066` (page 56, closing signature block) — plus two different support emails, `cskh@xanhsm.com` (page 45, note the different domain `xanhsm.com`) and `support.vn@greensm.com` (page 56, same as FAQ). Combined with FAQ's own `1555`, that's **four distinct phone numbers** across the corpus for what should be one hotline. All are recorded verbatim, none silently normalized to "the right one" — needs a real person to confirm which are current before `generate/prompt.py`'s `KHONG_BIET_TEXT` or any answer is trusted to recommend one.

### Retrieve gotchas (found by running against live data, not guessed)

- **`AITeamVN/Vietnamese_Reranker` doesn't load through `sentence_transformers.CrossEncoder`** on the pinned stack. The repo ships only `sentencepiece.bpe.model`, no pre-converted `tokenizer.json` (unlike `BAAI/bge-reranker-v2-m3`, which has both); `transformers==5.17.0` (pinned because `sentence-transformers==6.1.0` requires `transformers>=5,<6`) misdetects that raw sentencepiece file as tiktoken format during its on-the-fly fast-tokenizer conversion and fails — reproducible with every tokenizer class, even with `sentencepiece` installed. Downgrading `transformers` to `<5` isn't an option (hard conflict with `sentence-transformers`). Fix: `rag_gsm/retrieve/rerank.py` converts the tokenizer once via an ephemeral `uv run --with "transformers<5" --with protobuf` environment, caches the result at `~/.cache/rag_gsm/tokenizer_fix/`, then loads it under the pinned `transformers==5.17.0` (works fine once `tokenizer.json` exists) and scores with `AutoModelForSequenceClassification` directly instead of `CrossEncoder`. See `docs/kien-truc-code.md`'s "Bug thật" note under the retrieve task list for the full trail.
- `bm25s` has no LanceDB-style `prefilter` — there's no way to filter by metadata before it ranks. `hybrid.py` compensates by over-fetching (5× the branch's top-N) from BM25 then filtering `doi_tuong` after, which is safe here only because bm25s scores exactly (no ANN approximation) and the corpus is a few hundred chunks.

### Generate gotchas (found by running against live data, not guessed)

- **`qwen3:4b` is a reasoning model — its default "thinking" costs real latency, not just tokens.** Confirmed live: a one-chunk context took 65s / ~900 hidden tokens to answer; a real `retrieve_with_fallback` call over the full 337-chunk outline (PageIndex fallback branch) took **~103s** for one `generate_json` call. `OllamaAdapter`'s httpx timeout was raised from 120s (which really did time out on live data) to 300s. `"think": false` was tried as a fix and made things worse — on this Ollama build it doesn't suppress reasoning, it just relocates the whole reasoning blob into `message.content` with a raw `</think>` marker at the end, which would have leaked straight into a customer-facing answer if trusted blindly. Plain `generate()` calls (no `format: "json"`) do NOT leak `<think>` into `message.content` by default — Ollama returns the reasoning separately in `message.thinking`, which `OllamaAdapter` correctly ignores.
- **Citation `[n]` compliance is inconsistent, exactly as `05-retrieval.md`/`07-*.md` already flagged as an open risk before this was ever run.** Live test: `qwen3:4b` once emitted the literal string `[n]` instead of substituting a real index. This is not patched around — `generate/citation.py`'s regex only matches digits, so a literal `[n]` is silently ignored (no crash, no false citation), and `answer.citations` always lists every context block regardless of what the model actually cited. This is the reason that design was chosen, now confirmed against a real model rather than only in theory.
- `generate_json` (used by `fallback.py`) stayed fast and clean on a small outline (~1-2s, valid JSON, correct verbatim grounding) — the extreme latency above is specific to the *full 337-chunk outline* and to plain (non-JSON) `generate()` calls, not to `format: "json"` calls in general.
- **Resolved 2026-09-22: switched `generation.model`/`fallback.model` from `qwen3:4b` to `qwen2.5:3b`** (already pulled locally). Same prompt, same context: `qwen2.5:3b` answered in **3.4s** with **no hidden thinking** (`message.thinking` is `None`), vs. 65-103s+ for `qwen3:4b` — a ~20-100× speedup, and the answer was correctly grounded with the right `[1]` citation. Tradeoff found: `qwen2.5:3b` prepended a stray `"[Tất cả]"` token before the answer in that test — a minor prompt-compliance quirk not seen with `qwen3:4b` (smaller model, presumably weaker instruction-following) — worth watching in eval, not yet root-caused.
- **Bug thật 2026-09-23, found by the project owner clicking through the real UI: `qwen2.5:3b` answered a real question with the literal text `"[1]"` and nothing else** — no explanatory sentence at all. Reproduced deterministically (`done_reason: "stop"`, `eval_count: 4` — the model genuinely emitted EOS right after `[1]`, not a truncation/timeout in our code). Root-caused by ablating the system prompt: the old `SYSTEM_PROMPT` gave the citation-format instruction with a bare bracketed example ("...chèn ngay số thứ tự khối..., ví dụ [1] hoặc [2]") and no explicit instruction to *write an answer* — `qwen2.5:3b` pattern-matched onto the example itself as if it were the whole expected output, skipping the actual explanation. A `no_example` variant (same terse register, just moving where `[1]` goes) still failed the same way; only reframing the prompt as an explicit writing task ("viết một đoạn trả lời đầy đủ, tự nhiên...") plus an explicit negative constraint ("không bao giờ được trả lời chỉ bằng một trích dẫn trơ trọi") fixed it, verified against the failing question and two previously-working ones (no regression). This is a `qwen2.5:3b`-specific weak-instruction-following failure mode, not a citation-logic bug — `rag_gsm/generate/citation.py` and `answer.py` were never at fault, `Answer.text` is always exactly `llm.generate()`'s raw output by design. `tests/test_prompt.py::test_system_prompt_forbids_bare_citation_only_answer` pins the fixed prompt's wording so this can't silently regress if someone "simplifies" `SYSTEM_PROMPT` later.

### Eval gotchas (found by running against live data, not guessed)

- **A single slow/timed-out LLM call used to crash the entire eval batch and lose all prior progress.** `rag_gsm/eval/run.py` originally collected all rows in memory and wrote `eval/runs/<config_id>.jsonl` only at the end; a real `httpx.ReadTimeout` on question 1 (even at the 300s `OllamaAdapter` timeout — confirmed live, 300s is not always enough) killed the whole run with zero output. Fixed: each question's result is now written and flushed to disk immediately, and the per-question pipeline call is wrapped in `try/except Exception` — a failing question is recorded as a `"loi"` row and the batch continues.
- **A perfect retrieval score does not imply the `hybrid` branch fires.** Live smoke test (4 real golden questions, re-confirmed after the `qwen2.5:3b` switch): two paraphrased/no-diacritic queries had recall@5 = MRR = 1.0 at *every* layer including post-rerank (the correct chunk was reranked to position 1), yet the system still went to `khong_biet` — because the *rerank score* of that rank-1 chunk was **0.023 and 0.002** respectively, far below `thresholds.rerank_pass` (0.5), and the subsequent PageIndex fallback also failed to ground evidence. (For comparison, the two title-matching questions in the same 4-question batch scored 1.000 and 0.929 and correctly passed.) This is real, unguessed evidence that the 0.5 threshold and/or the reranker's confidence calibration need tuning against the full `eval/golden_questions.jsonl` — exactly the parameter Bước 9 exists to fix. `eval/run.py`'s output rows now include `top_rerank_score` and `fallback_node_list` specifically to make this diagnosable without re-running.
- `stdout` from `eval/run.py` is invisible in real time when redirected to a file/background task (Python fully buffers non-tty stdout) — per-question progress prints now pass `flush=True`.

### UI gotchas (found by running against live data, not guessed)

- **Bug thật, found twice by the project owner running the real command** (my first two "fixes" were both wrong): `uv run streamlit run rag_gsm/ui/app.py` failed with `ModuleNotFoundError: No module named 'rag_gsm'`. First wrong claim: "`streamlit run` adds the cwd automatically" — it doesn't. First fix attempt (adding `[build-system]`/hatchling to `pyproject.toml` so `rag_gsm` installs editable) was real and worth keeping, but I "verified" it by `curl`-ing the server's HTTP root and seeing 200 — **that's invalid**: Streamlit serves the static frontend shell on a bare GET without ever executing the app script; the script only runs once a browser's WebSocket session connects, so that check could never have caught this class of bug. The editable install alone still wasn't sufficient anyway — confirmed by re-testing with `streamlit.testing.v1.AppTest` (which *does* really execute the script the way Streamlit does) from a directory outside the project with no `PYTHONPATH`: same `ModuleNotFoundError`, reproduced on demand. **Actual fix:** `rag_gsm/ui/app.py` now inserts the project root into `sys.path` itself, at the top of the file, before importing anything from `rag_gsm` — makes the script self-sufficient regardless of how it's invoked, independent of packaging/editable-install/site.py subtleties. Verified this time with the *correct* method: the same adverse `AppTest` setup (outside the project, no `PYTHONPATH`) that reliably reproduced the bug now passes clean, including a full simulated chat round-trip. Lesson for next time: for a Streamlit (or any GUI-framework) bug, a bare HTTP/process-liveness check is not evidence the app logic ran — need something that actually executes the code path (a real page load via a client, or the framework's own test harness).
- **Nested `st.expander` works fine on Streamlit 1.64.0** — verified with `streamlit.testing.v1.AppTest` before writing `render_trace()`, since older Streamlit versions disallowed nesting. The "Xem prompt đầy đủ gửi LLM" expander is nested inside the main trace expander exactly as `08-streamlit-ui.md` specified, no workaround needed.
- **`streamlit.testing.v1.AppTest` is the way to verify a Streamlit app without a browser** (none is available in this dev environment) — it actually executes the script, runs real `st.cache_resource` loading (real bge-m3 + reranker + Ollama), and simulates widget interaction (`at.chat_input[0].set_value(...).run()`). Used to confirm live, end to end: the app loads without exception; a real question renders a user + assistant `ChatMessage` with a trace `Expander` containing the rerank dataframes; an off-topic question renders the fixed "không biết" text with the real hotline/email, with no exception either way. Two `AppTest`-specific quirks (unrelated to the import bug above): `AppTest.from_file()` needs an **absolute path** (a relative path resolves against the *calling test file's* directory, not the cwd or the app's own directory); `ChatMessage`'s role field is `.name`, not `.type` (`.type` is the generic element-type tag, always `"chat_message"`).
- This `AppTest`-based check is **not** part of `uv run pytest` — it needs a real Ollama server, a pulled model, and the real `index/public/` on disk, same category of "no offline test" as the embedder and reranker (see Known loose ends). It was run manually during development; there is no committed script for it, matching how `generate/run.py`'s and `eval/run.py`'s live checks are also manual, not part of the automated suite.

### Invariants any implementation must hold

These were each paid for with a measurement or a bug, and they cut across modules:

- **Headings are the contract** between ingest, PageIndex and citation. Build them from the document's own numbering (`1.` / `1.1.` / `1.1.1.`, FAQ group/question), never from what the converter inferred. The PageIndex tree *is* that skeleton.
- **Vietnamese is normalized twice**: NFC right after conversion, and diacritics stripped for BM25 tokenization (one index, syllable tokens — stripping diacritics moved MRR on undiacriticized queries from 0.25 to 0.94; word segmentation did not help and broke those queries).
- **Never threshold an RRF score** — it is rank-based and not comparable to cosine. The fallback threshold reads the **rerank score** (sigmoid-normalized top-1, `thresholds.rerank_pass`), not RRF and not raw dense cosine (rerank has already overridden that order) — see `docs/learning/05-retrieval.md`. *(Correction 2026-09-22: this line previously said "dense cosine top-1", which was wrong and never matched the config field name or `05-retrieval.md`'s own decision; `rag_gsm/retrieve/pipeline.py` implements the corrected version.)*
- **Filter before ranking** in LanceDB and pass `prefilter` explicitly; post-filtering silently returns too few rows or none. LanceDB returns `_distance`, so similarity is `1 - _distance`.
- **Isolation by structure, not just by filter**: `index/public/` and `index/internal/` are separate directories, and internal documents (`audience=noi_bo`) are never served to customers. A test must assert the public index leaks nothing internal.
- **`doi_tuong` labelling** (`nguoi_dung` / `doi_tac` / `chung`) is per-clause, because the general terms mix customer and partner obligations. Retrieval for customers takes only `nguoi_dung` and `chung`, and clauses with different labels must not be merged into one chunk.
- **Source trust is a label**, `nguon_tin_cay` (`chinh_thuc` / `bao_chi` / `cong_dong` / `noi_bo`); only official sources are indexed by default.
- **Keep the originals.** `data/raw/` is source of truth, Markdown is derived, so changing converters never means re-crawling or re-OCRing. `content_hash` skips unchanged documents.
- **Chunk ids are stable and citable**: `<doc>#<number>` (`general#3.2`, `faq#3.6`), a merged chunk spans a range (`general#3.2-3.4`). Citation is source URL + heading path, plus page number for image/PDF-derived text.
- **Every parameter needs an eval number**, not a guess — chunk size, k, thresholds, tokenizer, embedding model (bake-off on the GSM question set including one API model as a ceiling). Step 9 should also include a "stuff the whole corpus into the prompt" baseline: the text corpus is ~68–74k tokens, so RAG has to earn its place.
